# Troubleshooting

The questions that actually come up, with the real reason rather than a reassurance.

## Playback

### A song skipped by itself

Every source the app had for that track failed — a preview-only SoundCloud upload, a region-locked track, or a dead link. The app names the song it skipped rather than failing silently.

The same song is often available elsewhere: search it again and pick a row with a **different source badge**.

### Music stops when I leave the app

Your phone's battery optimiser killed the playback service.

Android lets manufacturers be aggressive here, and some are very aggressive. Find Relaxify in **Settings → Apps → Battery** and set it to **Unrestricted** (the wording varies: "Don't optimise", "No restrictions", "Allow background activity").

### Playback carried on after I swiped the app away

You are on a build before **v1.0.11**. Updating fixes it.

The cause was a binding held on the playback service: a service anything is still bound to cannot be destroyed by `stopSelf()`, so the request to stop was made and ignored. It only happened with the equalizer or normalization switched on, which is why it was easy to miss.

### The volume jumped when a song started

Fixed in **v1.0.9**. Enabling an audio effect on a live session makes Android re-route the audio, which is audible as a step in level, and the app was creating effects it was then not going to use.

Opening the **Equalizer screen** mid-song can still cost one, because reading your device's real band count requires a live effect. That one is unavoidable.

## Sound

### The equalizer says to play something first

Audio effects attach to a live audio session, and there is no session until something is playing. Start a song, then open the equalizer.

### It says the device refused the effects

Some handsets decline audio effects on an offloaded or fast-path audio route. That is the phone, not the app, and there is no way around it from inside an app.

The app reports **your device's own reason** rather than a generic message, precisely so this case is distinguishable from the one above.

### The equalizer bands will not drag smoothly

Fixed in **v1.0.11**. Before that the drag was recognised natively but everything it did afterwards crossed to the JavaScript thread on every frame.

If you are on v1.0.11 or later and a band still does not respond, check that the equalizer is actually **switched on** — a disabled band deliberately does not claim the touch, so the page scrolls over it instead.

## Search and downloads

### Search is slow or comes back with less than expected

The engine searches three public catalogues with a deadline and returns whatever arrived in time. A slow source **degrades** the results rather than hanging the search. Searching again with the caches warm usually finds the rest.

An entirely empty result almost always means no connection. The app works fully offline for downloads and not at all for search.

### A downloaded song is not showing as downloaded

Downloads are matched by **title and artist**, because a file on disk carries no catalogue identifier. If you edited those tags, the match is lost.

Re-downloading fixes it. The folder is re-scanned every time the Library tab is opened.

### Downloads fail or nothing is written

Storage permission was declined, or the chosen folder is on removable media that is no longer mounted. Check **Settings → Downloads → Download folder**, and re-grant storage if Android has revoked it for inactivity.

## Speed and battery

### The app drained the battery while I was not using it

Fixed in **v1.2.2**, and it was the app's fault rather than your phone's.

A one-second timer that exists to run crossfades never stopped running. Because playback keeps the process alive — deliberately, so music survives the screen going off — that timer kept ticking for as long as the process lived, which can be **days**. Every tick it asked the audio engine seven separate questions, one of which copied the entire queue across, whether or not anything was playing.

It now checks one thing first: is audio actually running. When nothing is playing the tick costs a single question and stops there.

### The app got slower to start the longer I used it

Fixed in **v1.2.2**. Two causes, both of which grew with use, which is why a fresh install always felt fine.

The home screen kept a copy of its last contents so it would have something to show instantly on the next launch. Nothing ever trimmed that copy, so it grew with the catalogue behind it — and all of it had to be read and parsed before the first frame could be drawn. It is now capped at what the screen actually shows.

Separately, the app read its saved data — playlists, likes, history, settings and a dozen more — as sixteen separate requests, one after another, all queued behind the same storage. It is one request now.

### Artwork takes a long time to appear on a slow connection

Much better from **v1.2.3**, and it was two separate wastes of the same bytes.

The coloured tint behind the player is taken from the cover, and reading that colour was downloading the picture a **second** time, at full size, on its own connection with no cache — while the real cover was being fetched alongside it and the song was trying to start on the same link. It now reads the small version, and Android caches it, so a cover you have seen before costs nothing at all.

Separately, a playlist row with no cover of its own draws a four-square mosaic of the songs inside it. Each of those squares is about 28 pixels across and each one was fetching a 500×500 image — four per row, for every row in your library.

### Long lists felt heavy to scroll

Improved in **v1.2.2**. Every row was fetching album art at 500×500 and drawing it at roughly a fifth of that, so each row downloaded and held about ten times the image it needed. Both catalogues can serve a smaller cover from the same address, so rows now ask for one.

The full player still uses the large artwork — that is the one place where it is the right size.

<Note title="If it still drains after v1.2.2">
  Check whether something is genuinely playing. A paused song still holds the playback service, which is normal and deliberate, but a song that is *playing* to a screen you are not looking at is not. **Settings → Diagnostics** shows what the app has been doing.
</Note>

## Interface

### The drawer will not open by swiping

The strip is the outer 28 pixels of the **left edge, on Home only**, and Android also uses that area for its own back gesture.

If your phone uses three-button navigation the conflict disappears. Either way, the hamburger in the Home header always works.

### No lyrics for this song

The Lyrics segment goes dim when the track genuinely has none on the provider — common for SoundCloud and YouTube uploads. It is not a failed fetch; the app checked and there is nothing there. See [Lyrics](/guide/lyrics).

### It said "the music engine stopped" when I opened the app, but everything works

Fixed in **v1.2.3**. The app watches its own embedded backend and says so when it stops answering — but it used to ask once and treat a single unanswered request as a death.

On a cold start that request is competing with the backend still unpacking itself, so it could fail while nothing was actually wrong. It now keeps asking for four seconds before it says anything, which a starting backend answers and a stopped one never does.

If you still see it *during* use rather than at launch, the notice is correct: your phone's battery manager killed the backend. Close the app fully and open it again, then exempt Relaxify from battery optimisation.

### Shuffle seemed to reorder the queue every time I pressed it

Fixed in **v1.2.4**, and turning it *off* was the broken half.

Shuffle reorders what is coming up and remembers the old order so that switching
it off can put it back. But the queue keeps moving while shuffle is on — songs
play, autoplay appends more — so putting that remembered list back was adding
songs you had already heard and dropping ones queued since. The result looked
just as random as switching shuffle on, so both directions appeared to reshuffle
and neither ever restored anything.

It now keeps the *order* it remembered but only the songs genuinely still ahead
of you, so off means off.

### The song that was playing crossfaded, but the next one did not

Fixed in **v1.2.4**. Each boundary is marked as faded so it cannot be faded
twice — but the mark used the track's **position** in the queue rather than its
identity. Start a different playlist and the numbering begins again, so a
leftover mark from the previous queue silently vetoed the fade on whichever song
landed on the same number. Repeat and previous hit it the same way.

### Crossfade only worked while I was looking at the app

Fixed in **v1.2.9**. The whole crossfade — noticing the end of the song,
starting the overlap, handing over to the next track — ran on JavaScript
timers, and Android stops those as soon as the screen goes off or another app
is in front. So it worked some of the time and not most of the time, depending
entirely on whether the phone was in your hand. It is scheduled natively now;
see [Sound](/reference/sound).

### Every song said 320 kbps

Fixed in **v1.2.9**. The quality badge fell back to the **Streaming quality**
setting when it had no better figure, and on Auto that meant 320 for every
song from every source. It now shows what the source reports for the stream it
actually handed over: YouTube's real stream bitrate (usually around 130), the
JioSaavn file that is really playing (320, 160 or 96), and SoundCloud's chosen
format (usually 128). If a source reports nothing, there is no badge.

### I turned Autoplay off and it kept playing

Fixed in **v1.2.4**. Autoplay tops the queue up a few songs *before* you reach
the end, so by the time you switch it off there are usually already eight
suggested songs sitting in the queue. Switching it off only stopped it adding
more — the ones already there still played, which made the setting look ignored.

Switching it off now also clears the suggestions still waiting. The song playing
right now is left alone, and anything you queued yourself is untouched.

### Back closes the wrong thing

It should close whatever is visually on top, one layer per press. If it does not on your build, that is a bug worth reporting with the exact sequence of screens — the ordering is explicit in the code and a wrong order is fixable.

## Updates

### The update dot never appears

Fixed in **v1.0.10**. The launch check used to skip for a full day after any "you're up to date", so a release published an hour later was invisible until the next day.

It now checks at launch and on every return to the foreground, at most once every fifteen minutes.

### I updated and lost my playlists

You uninstalled before installing. Android wipes app data on uninstall and there is no recovery.

Always install the new build **over** the existing app; the in-app updater does this correctly. Your downloads are unaffected either way — they live outside app storage.

## Still stuck

**Settings → Diagnostics** reports what the audio engine can see: whether the playback service is bound, which audio session is live, whether the effects attached, your device's real band count, and the last error it hit.
